# หลักความเป็นอิสระและขอบเขตงาน

เอกสารนี้กำหนดว่าผู้ตรวจอิสระ **ทำอะไร ไม่ทำอะไร** และระบบรับประกันความเป็นอิสระอย่างไร
ควรอ่านร่วมกันทั้งฝั่งผู้ตรวจและเจ้าของ repo ก่อนเริ่มงาน

## สิ่งที่ผู้ตรวจทำได้ (ตามสิทธิ์ Read)

- อ่านโค้ด ประวัติ commit และ PR ทั้งหมดใน repo ที่ได้รับสิทธิ์
- คอมเมนต์และเปิดประเด็นใน PR
- ส่งรีวิว: Approve / Comment / Request changes
- ระงับการ merge โดยไม่ approve หรือกด Request changes

## สิ่งที่ผู้ตรวจทำไม่ได้ (โดยโครงสร้าง ไม่ใช่โดยสัญญา)

- แก้ไข push หรือ merge โค้ดใด ๆ
- สร้าง ลบ หรือแก้ branch
- แก้ workflow, ruleset หรือการตั้งค่า repo
- เพิ่ม/ลบสมาชิก หรือเปลี่ยนสิทธิ์ของใคร
- อนุมัติ PR ที่ตัวเองเป็นผู้เสนอ — workflow บล็อกให้อัตโนมัติ

ข้อจำกัดเหล่านี้บังคับที่ระดับสิทธิ์ GitHub ไม่ใช่ข้อตกลงบนกระดาษ
ผู้ตรวจไม่มีทางฝ่าฝืนได้แม้ต้องการ

## หลักการที่ยึด

**แยกหน้าที่** — ผู้ตัดสินว่าผ่านหรือไม่ผ่าน ต้องไม่ใช่คนเดียวกับผู้ผลิตงาน
สิทธิ์ Read บังคับเรื่องนี้ให้เอง

**อนุมัติผูกกับสิ่งที่ตรวจ** — approve ผูกกับ commit SHA ที่ตรวจจริง
push ใหม่หลัง approve จะทำให้การอนุมัติหมดอายุทันที ไม่มีการอนุมัติแบบเหมารวม

**ตรวจสอบย้อนหลังได้** — ทุกการอนุมัติทิ้งร่องรอยไว้ใน review history ของ PR
พร้อม commit SHA และเวลา ลบไม่ได้

**ปฏิเสธได้โดยไม่มีต้นทุน** — ผู้ตรวจไม่มีส่วนได้เสียกับกำหนดส่งงาน
ไม่มีสิทธิ์ที่จะถูกถอนเป็นการลงโทษนอกจากถูกถอดออกจากทีมทั้งหมด ซึ่งเห็นได้ชัดใน audit log

## การเปิดเผยส่วนได้เสีย

ผู้ตรวจต้องแจ้งและถอนตัวจากการตรวจ เมื่อ:

- เป็นผู้เขียนหรือร่วมเขียนโค้ดใน PR นั้น
- มีส่วนได้เสียทางการเงินกับผลของการอนุมัติ
- มีความสัมพันธ์กับผู้เสนอ PR ที่กระทบการตัดสินอย่างเป็นกลาง

การถอนตัวทำโดยคอมเมนต์แจ้งเหตุผลใน PR แล้วไม่ส่งรีวิว
ถ้ามีผู้ตรวจคนเดียว ให้เจ้าของ repo หาผู้ตรวจสำรอง — ไม่ใช่ข้ามด่าน

## การป้องกันการข้ามด่าน

ชุดนี้ยับยั้ง PR ได้จริง แต่ **admin ของ repo ยังปิด ruleset หรือแก้ workflow ได้**
ถ้าต้องการความเป็นอิสระที่แข็งขึ้น ให้ทำเพิ่ม:

1. **ตั้ง ruleset ที่ระดับ organization** ไม่ใช่ระดับ repo — repo admin จะแก้ไม่ได้
   ที่ `https://github.com/organizations/<ORG>/settings/rules`
   โดย import `install/rulesets/org-independent-audit.json` ซึ่งตั้ง `protected: true`
   ไว้แล้วเพื่อไม่ให้เลี่ยงกฎด้วยการเปลี่ยนชื่อ repo
2. **ปล่อย bypass list ให้ว่าง** — ทุกคนรวมถึง owner ต้องผ่านด่านเดียวกัน
3. **จำกัดการแก้ไฟล์ workflow** ด้วย push ruleset ที่กันการแก้ `.github/workflows/**`
   (ฟีเจอร์นี้ตั้งได้ที่ระดับ organization และมีเงื่อนไขแผนสำหรับ repo private/internal)
4. **เฝ้าดู audit log** ขององค์กรที่เหตุการณ์ `repository_ruleset.*` และ `protected_branch.*`
   การปิดด่านจะปรากฏเป็นบันทึกที่ผู้ตรวจอ้างอิงได้

ถ้าเจ้าของไม่ยอมทำข้อ 1–2 ให้บันทึกไว้ในรายงานเป็นข้อจำกัดของขอบเขตการตรวจ

## สิ่งที่การตรวจนี้ไม่ใช่

การตรวจนี้ให้ความเห็นต่อโค้ดและกระบวนการที่เห็นใน repo เท่านั้น
ไม่ใช่การรับรองด้านความปลอดภัยแบบเต็มรูปแบบ ไม่ใช่ penetration test
ไม่ใช่การรับรองตามมาตรฐานบัญชีหรือกฎหมายใด ๆ และไม่ครอบคลุมสิ่งที่อยู่นอก repo
เช่น โครงสร้างพื้นฐานที่รันจริง ความลับที่เก็บนอกระบบ หรือขั้นตอนการ deploy ด้วยมือ
